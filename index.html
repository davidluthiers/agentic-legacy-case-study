01 · The problem

Huge platform, deep domain, few experts

I maintain the revenue-collection side of a large legacy platform: 445 Oracle Forms screens in that area alone, plus reports and PL/SQL packages.

  • A deep domain. Refunds of undue payments, offsets against enforced debt, public-sector accounting, SEPA payments. A wrong status can move real money.
  • Knowledge in a few heads. The rules live in screens, packages and old tickets, not in documentation.
  • A steady stream of incidents, each described as a symptom, not a stack trace.
  • Old tools. Forms/Reports, SVN, Jenkins, binary screen files. Nothing built with AI in mind.

The hard part is functional, not technical. Reading the code is easy. Knowing why a refund is stuck (which workflow, status or rule) is the job.

03 · A day in the life of an incident

From a new ticket to a published answer

  1. Agent

    08:00 · The routine starts

    Checks VPN and database access, then lists new and updated tickets.

  2. Agent

    Triage

    It moves accepted tickets to "in diagnosis": its only write to the tracker.

  3. Subagent

    Isolated analysis, one per ticket

    Classify symptom × area, search the catalogue, load the area skill, check the read-only mirror and compiled code; label each finding verified or inferred.

  4. Agent

    Ticket file and report

    A compact ticket file and a draft answer, the tracking sheet updated, and a closing "What I need from you".

  5. Human

    Review and decide

    I review the evidence, challenge the inferences and decide.

  6. Human

    Execute and publish

    I read and run any data fix myself and publish the answer. Each correction becomes a rule the same day.

Illustrative example · fictional data

Ticket: "A refund approved in March still hasn't reached the taxpayer."

  • VERIFIEDThe refund is recognised and posted; it sits in a payment batch that was never sent to the bank (batch status, read-only mirror).
  • VERIFIEDSame pattern as a catalogued case: refund stuck in an unsent batch.
  • INFERREDThe batch was left unsent after a bank-file rejection.
  • What I need from you: resend the batch, or move the refund to a new one?

My correction: the batch was not rejected; it was held on purpose for a guarantee check. I rewrote the answer, and the catalogue gained a "held batch" variant the same day.

27 corrections logged in the first month (15 Sep – 14 Oct 2026); a step earns more autonomy after 5 clean daily runs in a row.

04 · Guardrails & safety

Safety is enforced in code, not just requested

Humans decide and publish; the AI never writes to the database without permission.

A deterministic hook

A Python pre-tool-use hook, in both tools, intercepts database writes, repository changes, installs, edits outside the allowed folders and writes to the client's tracker.

Verified vs inferred

Verified: executed, or read in the code or the data. Inferred: deduced. Every finding carries one of the two.

Least privilege by environment

Research on a read-only production mirror, tests on the test environment, no production access: a human runs every script.

Privacy by design

For meeting minutes I built local transcription with speaker identification: the audio never leaves the laptop. Model calls run under my employer's commercial licences, and reports with client data are never published to external services.

06 · Design decisions & trade-offs

Why it is built this way

6.1Versioned skills instead of RAG

  • Exact identifiers matter: status codes, error messages, ticket numbers. Literal search finds them; similarity search blurs them.
  • Markdown in Git: I diff, review and revert knowledge like code. No infrastructure on a locked-down laptop.
  • Three access modes: always loaded (rules and links), read whole (one file per task), searched (catalogues keyed by literal codes).
  • Trade-off: manual curation, paid for with a fixed learning method and a validator.

6.2Deterministic hooks as well as instructions

  • Instructions are probabilistic: in one test, a session without the rules loaded wrote outside the allowed folders and ran a package install. Nothing stopped it.
  • The hook enforces the same rules in code, in both tools. It fails open on its own errors (failing closed would block all work on a hook bug): a safety net, not the only layer.

6.3Multi-model, tested on real tasks

  • One brain serves both Claude and GitHub Copilot.
  • A 13-test exam on real tasks, run 8 times on two models (one GPT, one Claude); failures became fixes.

6.4Context management by design

  • Context is cost. A fresh session starts at ~75k tokens; a resumed one reached ~726k, about ten times the cost of a fresh start.
  • Always-loaded context cut by 23% (61.7k → 47.2k characters), then the rules file again (30.1k → 27.3k), with no rule lost.
  • A pre-commit validator flags long skill descriptions (Copilot was silently dropping 7), oversized rule files and lines that search tools skip.
  • References split by sub-topic, growing catalogues kept out of the always-loaded level, links both ways: nothing orphaned.

6.5What went wrong, and what I changed

  • A resumed session hit ~726k tokens: now one session per ticket, handed over as a short ticket file.
  • 22 HTTP 400 errors in 66 session logs, all on one day and one client version: I debugged the tooling with data and filed a reproducible bug report, with temporary mitigations.
  • A failed diagnosis taught me that the code compiled in the database is the truth, not the working copy.

07 · Adoption & evolution

From my laptop to my colleagues'

Adoption

A packager builds a copy with no personal data and aborts if a username, name, e-mail or token is left; a test script simulates the install.

Two colleagues got it in its first week (a full install and a connections-only one, 15 and 16 October 2026), and more have asked for it.

It started with my manager: I had to convince them and teach them to use it, and every week they were more surprised by the speed and quality of the results.

Since that first installation

  • Oracle Forms as XML: read, edit and create screens. 461 converted with 0 errors, 445 of 445 round-tripped intact, new screens from a JSON spec, screenshots without running the app.
  • Remote builds and deployment to dev and pre-production from the command line.

08 · Lessons learned / what's next

Lessons learned and what's next

  1. Knowledge is the asset. Models change every few months; versioned domain knowledge compounds.
  2. Guardrails in code earn trust. Teams adopt what they can audit.
  3. Label verified vs inferred. The cheapest hallucination control I know.
  4. Next: measure. Time-stamp each routine step, so the next version reports measured numbers, not estimates.
